# Phase 2 contract spine (G014)

The `pa_engine.contracts` package is the language-neutral JSON boundary for
Phase 2.  It freezes 13 Draft 2020-12 artifact kinds at version `0.1.0`:
market snapshots and observation frames; analysis requests and policy;
knowledge citations and evidence packages; normalized model requests,
responses and call metadata; PA analysis results; decision and outcome events;
and the policy-to-outcome matrix.  The registry and fixture index live in
[`schema-index.json`](schema-index.json) and [`fixtures/fixture-index.json`](fixtures/fixture-index.json).

## Identity and canonical bytes

Canonical JSON is UTF-8 with compact separators (comma and colon), recursively lexical by object
key, and preserves array order.  Only JSON-native values are accepted; floats,
NaN and Infinity are rejected.  Prices, volume, ranges and confidence use the
exact decimal grammar frozen in the index: no exponent, trailing decimal point,
leading zero, or `-0`.  Timestamps are RFC 3339 UTC values ending in `Z`;
session interpretation uses an IANA time-zone name.

Each artifact's semantic projection removes only the volatile JSON pointers
explicitly listed for that kind in the index.  SHA-256 of that projection is
the `content_hash`; the kind's stable prefix plus that digest forms its top-level
ID (`mkt_`, `obs_`, `evi_`, `par_`, and so on).  Nested bar, observation,
evidence and idempotency IDs are generated by the helpers in `canonical.py`.
Changing a claim, page, price, or other non-volatile value changes the digest.

Correlation IDs, opaque provider request IDs, latency, token usage and event
recording timestamps are volatile telemetry and are excluded only where the
registry explicitly lists them.  In contrast, `analysis_request_id`,
`model_request_id`, response/call IDs, result IDs and their hashes are
content-derived semantic lineage; they must flow into downstream projections
and are not random request telemetry.

`knowledge_snapshot_id` is checked only for the relation
`kbs_` + `knowledge_snapshot_hash`.  G014 does not claim to implement the
full G013 manifest/chunks/records snapshot-digest algorithm; computing that
digest from the complete corpus belongs to G016.

## Result states, errors and uncertainty

`pa_analysis_result.status` is one of `signal`, `conditional`, `no_trade`,
`abstain`, or `error`.  A signal is an immediate buy/sell candidate;
`conditional` is explicitly `action=wait` and carries evidence-backed
conditions; no-trade, abstain and error use `action=none` and no trade levels.
Abstain/error envelopes carry a normalized error code.  A market-stage error
may be a valid pre-provider result: the analysis request remains non-null,
while market, observation, evidence and every model request/response/call pair
are explicitly `null`; no model artifact is fabricated.  An evidence-stage
abstain may retain market/observation/evidence lineage while all model pairs
remain `null`.  Knowledge confidence, model confidence and analysis uncertainty
are separate fields.  Warning, error and uncertainty code vocabularies are
frozen in the index, including partial-data, incomplete-last-bar, model-timeout,
invalid-model-response and grounding-failure cases.

Grounded setup/condition/level statements reference evidence IDs and claim IDs.
An evidence item resolves to a claim-level citation, which in turn resolves to
the local source, chunk, page range, source SHA and chunk-text SHA.  A
record-level citation is not claim-level grounding.  The canonical fixtures use
the formal Phase 1 MTR chain: record `rose-mtr`, field `market_context`, claim
`rose-mtr:market_context:1`, chunk `rose-mtr:intro-core`, page 1, source SHA
`9ade5b6c706cdeff09fba8effadffc1d0bda3c4a2004774232bae24ed094e5be`, and text
SHA `5670fc037d987c4eab886d5833fa0f1718db764627e6fd071975060f2b496372`.
Signal levels additionally use their own MTR entry, stop and target claims.
G014 validates exact IDs, declarations and linkage; semantic entailment of a
numeric level is a G018 finalizer responsibility.

## Policy matrix

`valid/policy_outcome_matrix.json` contains all 18 frozen conditions in
precedence order.  Every row records stage, terminal/continue disposition,
expected status and code, whether a model call is allowed, warnings,
uncertainty and incomplete-final-bar exclusion.  Market/evidence terminal
cases are pre-provider (`model_call_allowed=false`); allowed partial coverage
continues with a `partial_data` warning and high uncertainty.

## CLI

```bash
# Validate a standalone fixture (exit 0 valid, 1 contract-invalid, 2 read/JSON error)
python -m pa_engine.contracts validate \
  --file pa_engine/contracts/fixtures/valid/market_snapshot.json \
  --kind market_snapshot

# Validate a grounded artifact with its Phase 1 snapshot and related artifacts
python -m pa_engine.contracts validate \
  --file pa_engine/contracts/fixtures/valid/knowledge_evidence_package.json \
  --kind knowledge_evidence_package --knowledge-dir knowledge

# Compute the semantic SHA-256 and stable ID.  `hash` performs no schema,
# enum, lineage or grounding validation; run `validate` first.
python -m pa_engine.contracts hash \
  --file pa_engine/contracts/fixtures/valid/market_snapshot.json \
  --kind market_snapshot
```

The contract package imports no market-data or model-provider SDK and has no
network path.  Provider adapters, prompts, credentials and transport concerns
remain outside contracts; fixtures never contain credentials.  Phase 1
`knowledge/**`, `scripts/kb.py`, schemas and tests are read-only dependencies
for this slice and are not modified by contract validation.
